username → userLookupKey — Naming the Sign-In Lookup Key Honestly

Status: Draft — revised 2026-11-02 (×2: userID is a real PK, stays; username is not an email) Date: 2026-11-02 Precedes: fields-map & unified-register proposals — land this FIRST Scope: types/config_username_and_password.go, types/auth_interfaces.go, auth_implementation*.go, internal/**, docs/

Motivation

The package handles three distinct values, but names only two of them honestly:

NameWhereVerdict
userIDFuncUserLogout, FuncSessionCreate, FuncUserStoreAuthToken, GetCurrentUserID, types.AuthenticatedUserID, SessionInterface.GetUserID(), PostAuthHooks, ObservabilityHooksCorrect — keep. The host's real user-record primary key: returned by host callbacks (FuncUserLogin, FuncUserFindBy*, FuncUserRegister), stored in sessions, handed back unchanged.
emailFuncUserFindByEmail, FuncUserExists, email-send/template hooksCorrect — keep. Genuinely email addresses: lookup keys and delivery targets.
usernameFuncUserLogin(ctx, username, …), FuncUserFindByUsername, FuncUserPasswordChange(ctx, username, …), password-method FuncUserRegister(ctx, username, …)Wrong — rename. This is the sign-in lookup key: the string the user submits to locate their account. It is not an email (hosts may accept usernames, phones, member numbers) and it is not a userID (it's the key the lookup is performed with, not the row's PK). It is the host-defined lookup key.

The misnomer does real damage: FuncUserLogin(ctx, username, password) (userID, err) reads as if a username goes in and an ID comes out — when actually the lookup key the user signed in with goes in and the resolved primary key comes out. Two different values deserve two honest names:

// before — obscures that username→userID is a resolution step
FuncUserLogin func(ctx, username, password string, options) (userID string, err error)

// after — submitted lookup key in, resolved PK out
FuncUserLogin func(ctx, userLookupKey, password string, options) (userID string, err error)

Definition

userLookupKey — the host-defined key a user submits to locate their account at sign-in (username, email, phone, member number — the package does not constrain it). It is the input of the user lookup; contrast with userID, the record's primary key, which is the lookup's output and what sessions/tokens carry afterwards.

Name chosen over alternatives (decision 2026-11-02): userIdentifier — correct but near-synonymous with userID, invites conflation; userIdentity — misnames the value (identity = the principal, not the lookup key); loginIdentifier — fine but longer and method-flavored; userLookup — names the operation, not the value. userLookupKey names both the role (lookup) and the type (key) with zero overlap with userID.

Proposed Changes

1. Exported symbol rename — breaking, one symbol

BeforeAfterNotes
ConfigUsernameAndPassword.FuncUserFindByUsernameFuncUserFindByLookupKeyonly breaking rename. NOT merged with FuncUserFindByEmail — that hook looks up by email specifically; this one looks up by the sign-in lookup key, whatever the host defines it to be

Parameter names are non-breaking but renamed in the same pass — they are the documentation hosts read:

  • FuncUserLogin(ctx, username, password, …) → (ctx, userLookupKey, password, …)
  • FuncUserPasswordChange(ctx, username, newPassword, …) → (ctx, userLookupKey, newPassword, …)
  • FuncUserRegister(ctx, username, password, firstName, lastName, …) → (ctx, userLookupKey, …)
  • AuthPasswordInterface getter/setter signatures, deps structs, core/register_with_username_and_password.go and other internals, examples, tests.

2. Reserved key in the fields-map proposal

When the fields-map proposal lands, the reserved key for the password method's sign-in field is FieldUserLookupKey = "user_lookup_key" (not FieldUsername, not folded into FieldEmail) — the form field collects "how you sign in", which is the host-defined lookup key. Recorded here so the intent isn't lost if the proposals land in different releases.

3. What does NOT change

  • Every userID stays userID — types.AuthenticatedUserID, GetCurrentUserID, SessionInterface.GetUserID/SetUserID, SessionStoreInterface.SessionDeleteByUserID, PostAuthHooks, ObservabilityHooks, impersonation hooks. These are real primary-key values; the name is correct. (Revision note: an earlier draft renamed these to userIdentifier — withdrawn; PK values keep the honest name.)
  • Every genuine email stays email — FuncUserFindByEmail, FuncUserExists, email-send and email-template hooks, form field names. (Revision note: an earlier draft renamed username → email — withdrawn; the sign-in lookup key is not an email.)
  • Type/method names: ConfigUsernameAndPassword, NewUsernameAndPasswordAuth, core.RegisterWithUsernameAndPassword — see open questions.

4. Docs

  • docs/*.html signature tables updated.
  • README/doc comments: the "username(email) and password" wording becomes "lookup key and password" — the email-format validation on the built-in form is a default, not a definition.
  • CHANGELOG entry: FuncUserFindByUsername → FuncUserFindByLookupKey.

Ordering

Land this first, before the fields-map and unified-register proposals:

  • Pure rename, zero behaviour — safest break to ship in isolation.
  • Later proposals are written in final vocabulary (userLookupKey for sign-in, userID for the PK, email for emails). The unified-register hook's signature (ctx, userID, fields, options) is already correct under this vocabulary and needs no adjustment.

Risks / Open Questions

  • Type/method names containing "UsernameAndPassword": ConfigUsernameAndPassword, NewUsernameAndPasswordAuth, core.RegisterWithUsernameAndPassword describe the method (login name + password) rather than a parameter, so keeping them is defensible — "username" colloquially means "login name". Renaming to IdentifierAndPassword/EmailAndPassword is larger churn for marginal gain. Leaning: keep, and fix the doc comments instead.
  • FuncUserFindByLookupKey vs reusing FuncUserFindByEmail: deliberately kept separate — they search different keys (sign-in lookup key vs email). A host where lookup key == email implements both pointing at the same query; a host with real usernames needs both to exist independently.
  • No aliases: no deprecated FuncUserFindByUsername shim — clean cut, consistent with the package's approach elsewhere.
