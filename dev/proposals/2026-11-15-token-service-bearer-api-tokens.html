Token Service — Access/Refresh Bearer Tokens for SPAs and Mobile

Status: Proposed Date: 2026-11-15 Scope: types, internal/api, new internal/tokens, middlewares Inspired by: MadAppGang/identifo — token_service.go, token_storage.go, key_storage.go
⚠ POSSIBLY NOT NEEDED — largest speculative build (2026-11-15)
This is the largest speculative proposal in the set: a full token subsystem (service interface, 4 storage callbacks, refresh rotation with reuse detection, bearer middleware, 3 endpoints) for SPA/mobile clients the library has no confirmed consumer for. Gate this on a real consumer — a project that actually needs Bearer transport — before building. Note the callback contract also cannot deliver reuse detection as written (FuncRefreshTokenDelete destroys the evidence); a token-family model is required first.

Motivation

dracory/auth is cookie-session based, which fits server-rendered apps perfectly. But the JSON API (api_login, api_register, …) is already consumable by SPAs and mobile clients — where cookies are awkward (cross-site SameSite rules, no cookie jar on native, multi-tab edge cases). identifo solves this cleanly with a first-class token service abstraction — issue, validate, refresh, revoke — keeping signing keys and token persistence behind small storage interfaces.

Today a consumer of our JSON API must still depend on the auth cookie. A token service adds Authorization: Bearer as an opt-in second transport without disturbing the existing cookie flow.

Design

1. TokenService interface

// internal/tokens/service.go
type TokenService interface {
    // Issue creates a token pair for the given user.
    Issue(ctx context.Context, userID string, meta TokenMeta) (TokenPair, error)
    // Validate parses and validates an access token, returning its claims.
    Validate(ctx context.Context, token string) (Claims, error)
    // Refresh exchanges a refresh token for a new pair and rotates it.
    Refresh(ctx context.Context, refreshToken string) (TokenPair, error)
    // Revoke invalidates one token; RevokeAll invalidates all of a user's tokens.
    Revoke(ctx context.Context, token string) error
    RevokeAll(ctx context.Context, userID string) error
}

type TokenPair struct {
    AccessToken  string    `json:"access_token"`
    RefreshToken string    `json:"refresh_token"`
    ExpiresAt    time.Time `json:"expires_at"`
    TokenType    string    `json:"token_type"` // "Bearer"
}

2. Callback-based persistence (consistent with existing style)

Following the library's bring-your-own-database convention, refresh tokens are stored via config callbacks — no concrete store is bundled:

// types/config_tokens.go
type ConfigTokens struct {
    Enabled         bool
    Issuer          string        // iss claim; defaults to the site name
    AccessTokenTTL  time.Duration // default 15m
    RefreshTokenTTL time.Duration // default 720h (30d)
    SigningKey      []byte        // HS256 to start

    FuncRefreshTokenStore     func(ctx context.Context, userID, tokenID string, expiresAt time.Time) error
    FuncRefreshTokenExists    func(ctx context.Context, tokenID string) (userID string, err error)
    FuncRefreshTokenDelete    func(ctx context.Context, tokenID string) error
    FuncRefreshTokenDeleteAll func(ctx context.Context, userID string) error
}

3. Endpoints (opt-in)

  • POST /api/auth/login — gains a tokens object in the JSON response when ConfigTokens.Enabled; the cookie is still set for web clients, or omitted with ?transport=bearer
  • POST /api/auth/token/refresh — rotates the refresh token, returns a new pair
  • POST /api/auth/token/revoke — revokes the presented token
  • New middleware ApiAuthBearerMiddleware — accepts either the auth cookie or a valid Authorization: Bearer access token

4. Refresh-token rotation with reuse detection

Every refresh issues a new refresh token and deletes the old one. Presenting a deleted-but-unexpired token indicates theft — the entire user token chain is revoked (per the OAuth 2.0 Security BCP).

Security

  • Refresh tokens are opaque random IDs, never JWTs — revocable server-side
  • Access tokens are short-lived (≤15m) so revocation lag is bounded
  • Refresh/revoke endpoints run under ConfigRateLimiting
  • Token JSON is never emitted on cookie-based HTML flows
  • Password reset already invalidates sessions — extend it to RevokeAll

Out of Scope (v1)

  • Acting as an OIDC provider (JWKS endpoint, /.well-known) — identifo does this, but AuthKnight already covers delegated OIDC for us
  • Asymmetric signing (RS256) — the interface permits it later via a key-getter callback
  • Token introspection endpoint for third parties
