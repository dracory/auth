Message Catalog — Externalized UI & Email Strings

Status: Draft — revised 2026-11-15 (page copy now covered by PageOptions; scope narrows) Date: 2026-11-15 Scope: internal/ui/*, internal/emails, internal/api responses, types Inspired by: MadAppGang/identifo — localization/
⚠ POSSIBLY NOT NEEDED — review before implementing (2026-11-15)
Most of this proposal's value was absorbed by ConfigShared.PageOptions + LegalLinks, which shipped 2026-11 and cover page-copy relabeling. What remains (API error strings, email templates, per-request locale) may not justify a full Messages map + fallback machinery + per-locale resolution. No host has requested i18n. A much smaller "override these N error strings" config would cover the actual need — shrink or defer until a real consumer asks for it.

Motivation

identifo externalizes all user-facing strings into a localization layer. dracory/auth's UI pages (internal/ui/page_*), email templates, and API error messages are hardcoded English. Hosts that need another language — or simply want to reword "Sign in" → "Log in" — must fork the pages.

Doing this now is cheap: the string set is small and page templates already funnel through shared helpers. Doing it later means touching every label retroactively.

Update 2026-11-15 — partial overlap resolved: since this proposal was drafted, ConfigShared.PageOptions + LegalLinks shipped (2026-11, see 2026-11-06-page-customization-and-legal-links.html) and cover most page-copy relabeling needs. The remaining scope for a message catalog is: public-facing error strings returned by internal/api, email templates in internal/emails, and any copy hosts need to vary per-request (per-locale) rather than per-deployment. types/messages.go already centralises the constants but they are not yet overridable — this proposal is what makes them so.

Design

1. A flat message map, not an i18n framework

// types/messages.go
type Messages map[string]string

// Keys are stable, namespaced constants:
//   ui.login.title, ui.login.submit, ui.register.email_label,
//   email.password_reset.subject, error.invalid_credentials, ...

func (m Messages) Get(key string) string {
    if s, ok := m[key]; ok { return s }
    return DefaultMessages[key] // English fallback — never a missing key
}

2. Config hook

type ConfigShared struct {
    // ...
    // Messages overrides DefaultMessages per key. Optional.
    Messages Messages
    // FuncLocale resolves a request to a locale tag. Optional;
    // used only when FuncMessages per-locale is configured.
    FuncLocale func(r *http.Request) string
}

3. Plural/locale strategy

  • v1: one Messages map per instance — covers relabeling and single-language non-English deployments (the realistic case for our hosts)
  • v1.1 (optional): Messages map[string]Messages keyed by locale + FuncLocale request resolution — added only if a host asks
  • Strings that need interpolation use text/template-style {{.Code}} placeholders, rendered at use site

Scope of Strings

  • All labels, headings, buttons, flash messages in internal/ui/page_*
  • Email subject + body templates in internal/emails
  • Public-facing error strings returned by internal/api (error codes stay fixed — they're the machine-readable contract)

Compatibility

Fully additive: default map equals today's strings, so existing hosts see no change. Templates receive msg "ui.login.title" instead of literals — internal refactor only.

Out of Scope

  • Pluralization rules, CLDR data, date/number formatting
  • RTL layout variants
  • Loading translations from files (hosts embed or hardcode the map)
