dracory/auth — proposal

Multi-Client Redirect Whitelist — Per-App Allowed Return URLs

Status: Proposed Date: 2026-11-15 Scope: internal/rules, types, login/logout/register flows Inspired by: MadAppGang/identifo — app_storage.go, origin_checker.go

Motivation

identifo scopes auth to registered applications: each app has an ID and a whitelist of allowed redirect/origin URLs, so a hosted login page can safely return users to several different front-ends (marketing site, dashboard, mobile deep link) without becoming an open redirector.

dracory/auth has safeReturnPathRule — which only allows same-origin paths. That is correct and safe for the single-app case, but the ecosystem is growing a pattern where one auth instance serves several sibling properties (e.g. app.example.com, docs.example.com, AuthKnight-style cross-site login). Currently a host must write custom redirect validation to allow any external URL.

Design

1. Allowed-origins config

// types/config_redirects.go
type ConfigRedirects struct {
    // AllowedRedirectOrigins are additional origins (scheme+host[:port])
    // that return_to/redirect params may point to, beyond same-origin paths.
    // Example: []string{"https://app.example.com", "https://docs.example.com"}
    AllowedRedirectOrigins []string
}

2. Generalize safeReturnPathRule

The rule gains a second stage — unchanged behavior by default:

  1. Parse the candidate URL; reject unparseable and protocol-relative (//evil.com) values
  2. Relative path → allow (current behavior)
  3. Absolute URL → allow only if scheme+host[:port] exactly matches an entry in AllowedRedirectOrigins; otherwise fall back to the default path
  4. Only http/https schemes — javascript:, data: etc. always rejected

3. Optional client registry (deferred)

identifo's fuller model (per-app secrets, per-app user pools) is noted but not proposed: an origin allowlist covers our real need — trusted cross-site return — without introducing a client concept into the library. If a future need arises (per-client branding, per-client methods), this config grows into a Clients []Client struct without breaking the allowlist.

Security

  • Exact origin match only — no wildcards, no subdomain globbing (*.example.com is a documented anti-pattern)
  • Empty list = today's strict same-origin behavior (secure default)
  • Applied uniformly: login success redirect, logout redirect, register return_to, magic-link next
  • Redirects to rejected origins log a warning via slog (attack signal)

Out of Scope

  • Per-client method enablement, branding, or user-pool isolation
  • Dynamic client registration API
  • CORS origin checking for the JSON API (separate concern, host middleware)
