dracory/auth — proposal

Extensible Registration & Profile-Completion Fields

Status: Draft — revised to match current code Date: 2026-10-31, revised 2026-11-02 Scope: types/, auth_implementation.go, internal/ui/page_register (+ shared), internal/api/api_register, internal/api/api_register_code_verify, internal/core, internal/rules, utils/

Motivation

Two gaps force host projects to shadow /auth/register with their own controllers (dogpace.com-golang does exactly this — internal/controllers/auth/register_password and internal/controllers/auth/register):

  1. Fixed field set. The built-in register forms only collect first_name, last_name, email, password. Hosts commonly need country, timezone, phone, business name, birthday, etc. Peers solve this with declared field schemas (better-auth additionalFields, SuperTokens form fields, Keycloak declarative user profile). Our callback-driven storage model fits the same approach — the host already persists whatever it wants inside FuncUserRegister; it just never receives the values.
  2. Fixed field set in profile completion too. Update 2026-11-02: the completion half of this gap is now solved — rules.NewProfileCompletionRule detects an authenticated session on the register request, page_register renders RegisterCompletionContent (read-only verified email), and api_register routes to FuncUserProfileUpdate(ctx, userID, firstName, lastName, options) instead of creating a user. PostAuthHooks.RegistrationComplete already lets the package redirect incomplete users to /auth/register. Additionally ConfigShared.UserCreationPolicy now offers CreateUserOnRegister: verified-but-unknown emails get a token and register by creation — no row, no session — via RegisterFirstRule. What remains is that the completion form is hardcoded to first/last name — the same fixed-field-set problem as registration, on the update path.
  3. No registration-time allowlist hook. PostAuthHooks.EmailAllowed runs only inside the post-auth pipeline (internal/core/post_auth.go) and in api_magic_link_send; PostAuthHooks.RegisterRules also fires post-auth, too late. Nothing stops a disallowed email from hitting POST /auth/api/register before a verification code is generated. Hosts enforcing an allowlist must still shadow the endpoint.

Design Principles

  • One consistent break — flat map. All user-write hooks take the fields map, credentials included: FuncUserRegister collapses to a single (ctx, fields, options) signature across all three methods, and FuncUserProfileUpdate becomes (ctx, userID, fields, options) (userID stays positional — it's the row identity, never a form field). Breaking, deliberately (decision 2026-11-02): a uniform data contract outweighs a mechanical host migration. Reserved keys email, password, first_name, last_name are always populated — by the form or injected server-side (verified-token/completion flows) — and raw storage (see escaping proposal) is what makes password safe in the map.
  • Host-declared, package-rendered. Hosts describe fields in config; the built-in pages render Bootstrap markup matching the existing FieldGroup/NameRow style.
  • Server-side truth. Client-side validation is UX only; every field is re-validated (required + custom Validate) in the API before the values reach host code or the temp-key payload.
  • Minimal v1. Static select options only — no dynamic option providers, no conditional fields, no JSON-schema engine.

Proposed Changes

1. Field schema — new types/fields.go

package types

// FieldType enumerates the HTML input kinds the built-in pages can render.
type FieldType string

const (
    FieldTypeText     FieldType = "text"
    FieldTypeEmail    FieldType = "email"
    FieldTypeTel      FieldType = "tel"
    FieldTypeDate     FieldType = "date"
    FieldTypeNumber   FieldType = "number"
    FieldTypeSelect   FieldType = "select"
    FieldTypeCheckbox FieldType = "checkbox"
)

// FieldOption is one <option> in a FieldTypeSelect field.
type FieldOption struct {
    Value string
    Label string
}

// RegistrationField declares one extra input rendered on the built-in
// register / profile-completion pages and validated server-side.
type RegistrationField struct {
    Name         string        // form field name, e.g. "country"
    Label        string        // rendered above the input, e.g. "Country"
    Type         FieldType     // empty => FieldTypeText
    Required     bool
    Placeholder  string
    Options      []FieldOption // FieldTypeSelect only
    Autocomplete string        // e.g. "tel", "bday", "country-name"
    // Validate optionally inspects the submitted value and returns an
    // error message; "" means valid.
    Validate func(value string) string
}

Predefined-field catalog + name shorthand. The full struct is the maximum-flexibility path, but the common case is "pick known fields by name". The package ships a small registry (added 2026-11-02):

// DefaultFields maps well-known field names to ready-made
// RegistrationField declarations (labels, types, autocomplete, options).
// v1 catalog: first_name, last_name, country, timezone, phone, birthday.
var DefaultFields = map[string]RegistrationField{ /* ... */ }

// Fields resolves names through DefaultFields in argument order.
// Unknown names panic at config time — fail fast, not at request time.
func Fields(names ...string) []RegistrationField

Usage:

RegistrationFields: types.Fields("first_name", "last_name", "country"),
  • Ordering = argument order; results are mutable — hosts needing a custom label or Validate post-process the returned slice (fs[0].Label = "Country of residence") or write the full struct for that field.
  • Selects ship static Options (country/timezone lists live in types, reused by hosts' own needs).
  • With no args Fields() can return the completion default {first_name*, last_name*}, so ProfileFields: types.Fields() spells today's behaviour explicitly.
  • Non-goal: the catalog stays small and English; i18n was already the host's problem (labels are strings).

ConfigShared gains:

// RegistrationFields are extra inputs rendered on the public sign-up
// form (all methods) after the built-in fields. Collected values are
// delivered to FuncUserRegister via UserAuthOptions.Fields.
RegistrationFields []RegistrationField

// ProfileFields are inputs on the profile-completion form — the
// existing ProfileCompletionRule branch in page_register /
// api_register for authenticated users with incomplete profiles
// (CreateUserOnAuth sessions, legacy rows) whose email is already
// verified and shown read-only. Under CreateUserOnRegister the
// same-looking form is registration-by-creation and uses
// RegistrationFields instead. Values are delivered to
// FuncUserProfileUpdate.
ProfileFields []RegistrationField

// FuncRegistrationAllowed optionally gates registration before any
// code is generated or email sent — e.g. an email allowlist.
FuncRegistrationAllowed func(email string) (allowed bool, message string)

// FuncUserProfileUpdate persists completion-form values for an
// existing authenticated user. BREAKING: signature changes from
//   (ctx, userID, firstName, lastName string, options)
FuncUserProfileUpdate func(ctx context.Context, userID string, fields map[string]string, options UserAuthOptions) error

// FuncUserProfile optionally returns current values to prefill the
// completion form; missing keys render empty inputs.
FuncUserProfile func(ctx context.Context, userID string, options UserAuthOptions) (map[string]string, error)

2. UserAuthOptions carries field values

type UserAuthOptions struct {
    UserIp    string
    UserAgent string
    // Fields holds values for the declared RegistrationFields /
    // ProfileFields plus reserved keys populated by the built-in
    // inputs or injected server-side (see FieldName constants).
    // nil when no fields exist.
    Fields map[string]string
}

// Reserved field names — populated and REQUIRED by the package.
// They are internally modelled as required built-in fields: the API
// validates their presence before any host hook is invoked, so a
// missing key is a rejected request, not a silent empty lookup.
// They may never be declared as RegistrationField.Name — collisions
// are rejected at config time.
const (
    FieldEmail     = "email"      // required on every register path;
                                  // on the token branch it is injected
                                  // from the resolved verified_key
    FieldUsername  = "username"   // required on the username+password method
    FieldPassword  = "password"   // required on the username+password method
    FieldFirstName = "first_name" // required built-in input
    FieldLastName  = "last_name"  // required built-in input
)

Hook signatures flattened — breaking (decision 2026-11-02). All FuncUserRegister variants collapse to one signature:

// ConfigOtp — was: (ctx, email, firstName, lastName, options) (err)
// ConfigUsernameAndPassword — was: (ctx, username, password, firstName, lastName, options) (err)
// ConfigAuthKnight — was: (ctx, email, firstName, lastName, options) (userID, err)
FuncUserRegister func(ctx context.Context, fields map[string]string, options UserAuthOptions) (userID string, err error)
  • Key taxonomy (documented + enforced contract): reserved keys (Field* constants) are package-populated and required — modelled internally as required built-in fields so the API rejects a request missing email/password/first_name/etc. before the host hook runs (missing key = error response, never an empty lookup in host code). On the verified-token branch email is injected from the resolved token rather than read from the form. Declared keys come from host RegistrationFields/ProfileFields validated by CollectFields; declared names colliding with reserved keys are rejected at config time.
  • password travels raw (no escaping — see escaping proposal), never prefills, never logs.
  • Uniformity pays off: one signature serves all three methods; fields["username"] is set only on the username+password method, fields["password"] only where a password was collected.
  • Migration is one mechanical edit per host implementation: fields[types.FieldEmail] for email, etc.

3. Field validation helper — internal/rules or utils

// utils/collect_fields.go (shared by api_register branches and core)
func CollectFields(r *http.Request, fields []types.RegistrationField) (map[string]string, *FieldError)
  • Reads req.GetStringTrimmed(r, f.Name) for declared names only — undeclared form keys are ignored (no injection vector).
  • Reserved keys are required built-ins: callers prepend the method's reserved field set (email, password, first/last name per the active branch) to the declared list, so the same required-check path enforces presence — a missing reserved key fails validation before any host hook runs.
  • Stores raw trimmed values — no escaping at collection (escape-at-render only; see 2026-11-02-store-raw-escape-at-render.html). This is what makes credential keys like password safe in the map.
  • Required → non-empty; Validate → must return ""; select → value must be in Options (prevents forged values).
  • Returns first failure as a user-facing message.

4. Page rendering — internal/ui/shared/components.go + page_register

New component:

// shared/components.go
func FieldInput(f types.RegistrationField, value string) hb.TagInterface
  • maps FieldType → hb.NewInput().Type(...) or hb.NewSelect() with Options; applies required, placeholder, autocomplete, form-control form-control-lg; pre-selects value for prefill.

page_register — update 2026-11-02: the page now has four content builders (RegisterAuthKnightContent was superseded by RegisterVerifiedEmailContent, and RegisterCompletionContent was added). Each gains a fields parameter and renders shared.FieldInput(f, value) after NameRow/email and before PrimaryButton:

  • RegisterOtpContent(urlLogin, fields) — RegistrationFields
  • RegisterUsernameAndPasswordContent(urlLogin, urlPasswordRestore, fields) — RegistrationFields
  • RegisterVerifiedEmailContent(urlLogin, verifiedEmail, verifiedKey, fields) — RegistrationFields
  • RegisterCompletionContent(urlLogin, verifiedEmail, fields, prefill) — ProfileFields + FuncUserProfile values (see §7)

PageRegister passes a.GetRegistrationFields() / a.GetProfileFields() (optional-interface resolution, see §8).

5. JS serialization — register_*.js

Each register page embeds the declared field names via a template placeholder injected next to the existing __URL_API_REGISTER__ ones:

var extraFieldNames = __EXTRA_FIELD_NAMES__; // e.g. ["country","phone"]

In registerFormValidate(): after built-in validation, loop extraFieldNames, inputVal(name) (checkbox → checked flag as "true"/""), client-side required check, then merge into the postForm body. Names arrive JSON-encoded so markup stays safe.

6. API + payload flow

api_register.go — profile-completion branch (first, unchanged ordering): the existing ProfileCompletionRule block collects ProfileFields via CollectFields (instead of hardcoding first/last name) and calls deps.UserProfileUpdate(ctx, userID, fields, options). Default ProfileFields when unset: first/last name required — today's behaviour preserved verbatim.

api_register.go (RegisterOtpInit + password branch): collect & validate fields via CollectFields; merge the reserved keys (email, password, first_name, last_name) into the same map; add "fields": map[string]string to the registercode: JSON payload (passwordless) or pass straight into options.Fields (password, no-verification branch via core). Invoke FuncRegistrationAllowed(fields["email"]) before code generation — failure returns api.Error(message). Host call becomes FuncUserRegister(ctx, fields, options) per §2.

core/register_with_username_and_password.go: signature unchanged; fields arrive inside options.Fields (the caller deps.RegisterWithUsernameAndPassword in api_register.go collects them). Validation + FuncRegistrationAllowed run there too; "fields" added to the verify-enabled JSON payload (line ~112).

api_register_code_verify.go: extract registerMap["fields"] (map[string]any → map[string]string) — now carrying first/last name inside the map, so the separate first_name/last_name payload keys are kept only for old-payload fallback (merged into the map when "fields" is absent); the deps wrappers (OtpUserRegister, UserRegister) adopt the flat (ctx, fields, options) host signature, and ApiRegisterCodeVerifyWithAuth sets options.Fields = fields when invoking them.

Verified-email / AuthKnight register (api_register.go token branch): update 2026-11-02: the AK branch was generalised — a posted verified_key now resolves via VerifiedEmailKeyRule under registerMu. Same treatment: collect + validate fields, inject the token-resolved email into the map, pass via options.Fields into vDeps.UserRegister(ctx, fields, options).

Backward compatibility: old payloads without "fields" unmarshal to nil map — hosts see options.Fields == nil.

7. Profile-completion flow (the OTP case) — already landed, needs generalising

Update 2026-11-02: the separate page_profile_completion + api_profile_completion + multi_method.go mounts originally proposed here are no longer needed. The flow now exists inline:

  • rules.NewProfileCompletionRule(resolveUserID, r) (internal/rules/profile_completion_rule.go) — an authenticated session on the register request means "update, don't create".
  • page_register → RegisterCompletionContent(urlLogin, verifiedEmail) renders the read-only email (form-control-plaintext, never read back from the form) + hardcoded first/last name.
  • api_register → the same rule routes to deps.UserProfileUpdate(ctx, userID, firstName, lastName, options) and returns MsgProfileSaved + {redirect: deps.RedirectOnSuccess}.
  • PostAuthHooks.RegistrationComplete(ctx, userID) (types/post_auth.go) — the package already gates: incomplete users are bounced back to /auth/register before RedirectURL is consulted. This is exactly the FuncProfileComplete "future iteration" floated in the original draft — it landed first.

Policy caveat (revised 2026-11-02): completion only exists under CreateUserOnAuth (the default), where verify-time UserFindByEmailOrCreate can leave incomplete rows. Under CreateUserOnRegister, RegisterFirstRule gives verified-but-unknown emails a token and sends them to the verified-email register form — a create path using RegistrationFields, no session, no row. The completion branch stays relevant for on_auth hosts and any incomplete accounts that already exist.

What this proposal now adds on top:

  • RegisterCompletionContent gains fields + prefill parameters; renders ProfileFields via shared.FieldInput(f, prefill[f.Name]), prefill from FuncUserProfile when set.
  • The API branch swaps the hardcoded first/last validation for CollectFields(r, profileFields) and calls the new FuncUserProfileUpdate(ctx, userID, fields, options) signature (§1). When ProfileFields is unset the package defaults to {first_name*, last_name*} so existing behaviour and the current form markup are preserved.
  • register_completion.js gains the same __EXTRA_FIELD_NAMES__ serialization as the other register scripts.
  • No new routes, no multi_method.go changes — the trigger stays RegistrationComplete → /auth/register, already wired.

9. Dogpace-side follow-up (documented, not part of this package change)

Once this lands, dogpace.com-golang:

  • deletes internal/controllers/auth/register_password entirely
  • replaces internal/controllers/auth/register with ProfileFields + FuncUserProfileUpdate (vault-tokenizing) config; completion redirects already work via the existing PostAuthHooks.RegistrationComplete → /auth/register path — dogpace just backs it with its IsRegistrationCompleted check
  • wires FuncRegistrationAllowed to authrules.NewEmailAllowedRule

Explicitly Out of Scope

  • Dynamic option providers (OptionsFunc), cascading selects, conditional fields.
  • JSON-Schema identity traits (Kratos-style).
  • Profile editing after completion (settings page) — same machinery, later.
  • Field ordering beyond declaration order; field grouping/rows.
  • Translatable labels (labels are host-supplied strings — already the host's problem).

Risks / Open Questions

  • Escaping direction — decided: store raw, escape at render (2026-11-02-store-raw-escape-at-render.html). The existing escape-at-collection sites get fixed there; this proposal inherits raw storage so prefill never double-escapes.
  • Checkbox semantics: "true"/"" string encoding documented for hosts.
  • Select with 400+ options (timezones): acceptable statically; flag that a SelectMultiple or AJAX provider is future work if UX suffers.
  • Breaking hook signatures — accepted: FuncUserRegister flattens to (ctx, fields, options) for all variants and FuncUserProfileUpdate to (ctx, userID, fields, options) — credentials and profile data all travel in the map, discriminated by the reserved-key taxonomy (Field* constants). Done once, correctly, rather than a split-parameter API or parallel *Fields hooks forever. Migration is mechanical (fields[types.FieldEmail], fields[types.FieldPassword], …). Presence is enforced, not conventional: reserved keys are required fields — requests missing them are rejected before the host hook runs, so host code can rely on non-empty lookups.
  • Register vs completion field overlap: first/last name are built-in inputs on the register form (delivered as reserved map keys) but declared ProfileFields defaults on the completion form — acceptable asymmetry, documented.
