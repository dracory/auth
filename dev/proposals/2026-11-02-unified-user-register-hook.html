Unified FuncUserRegister — One Hook for Create & Complete

Status: Draft Date: 2026-11-02 Depends on: 2026-11-02-user-lookup-key-naming.html, 2026-10-31-extensible-registration-and-profile-fields.html Scope: types/, auth_implementation.go, internal/api/api_register, internal/api/api_register_code_verify, internal/core, new_*.go

Motivation

The package currently carries four host callbacks that all do the same thing — persist the registration form against a user record:

// ConfigUsernameAndPassword — create with credentials
FuncUserRegister func(ctx, username, password, firstName, lastName string, options) (err error)

// ConfigOtp — create without credentials
FuncUserRegister func(ctx, email, firstName, lastName string, options) (err error)

// ConfigAuthKnight — create, already email-verified; returns the new ID
FuncUserRegister func(ctx, email, firstName, lastName string, options) (userID string, err error)

// ConfigShared — update an existing user (profile completion)
FuncUserProfileUpdate func(ctx, userID, firstName, lastName string, options) (err error)

From the host's perspective there is no meaningful difference between the four: in every case the host registers the user — writes the submitted profile fields to a row. Whether that row is inserted or updated is an implementation detail of the same operation. Profile completion is literally called "registration" by the package itself: incomplete users are bounced to /auth/register and shown a registration form — they simply happen to already have a row (created implicitly at first OTP/magic-link login).

Splitting this into four hooks has real costs:

  • Host duplication. A host supporting passwordless registration + completion must implement the same persistence code twice — once as FuncUserRegister (find-or-create by email) and once as FuncUserProfileUpdate (update by ID). The fields map proposal makes this even more obvious: both hooks would receive the identical map[string]string payload.
  • Signature drift. The three register variants already differ for no good reason — only AuthKnight returns userID. The password variant returns nothing and forces the package to re-look-up the user via FuncUserFindByUsername right after registration, a second query that exists only because the hook can't hand the ID back.
  • Config sprawl. The same conceptual hook is declared in four different config structs with four different shapes.

Design Principles

  • Registration is upsert. One hook serves create and update: userID == "" → create a new record and return its ID; userID != "" → update that record and return the same ID. The host decides how (INSERT vs UPDATE); the package just delivers identity + fields.
  • Builds on the fields-map proposal. This proposal assumes — and composes with — 2026-10-31-extensible-registration-and-profile-fields.html: the hook takes fields map[string]string with the reserved-key taxonomy (email, username, password, first_name, last_name) plus host-declared RegistrationFields/ProfileFields. If that proposal lands first this is a pure merge; the two can also land together as one break.
  • One consistent break. All four hooks collapse into a single ConfigShared hook. Breaking, deliberately — same reasoning as the fields-map flattening: a uniform contract outweighs a mechanical host migration.
  • userID stays positional. It is row identity, not a form field — never travels in the map (consistent with the existing decision on FuncUserProfileUpdate).
  • Positional parameter is userID. The value is the user record's primary key — the honest name, per the naming proposal (see §7). The sign-in lookup key (userLookupKey) and email are different values that travel inside fields, never positionally.

Proposed Changes

1. The unified hook — types.ConfigShared

// FuncUserRegister persists the registration form for a user.
//
// userID == ""  → create a new user record from fields and return
//                 its identifier.
// userID != ""  → update the existing user (profile-completion path:
//                 the user is authenticated; fields contain ProfileFields
//                 values, never credentials) and return the same identifier.
//
// Reserved keys populated per method (all required — validated before
// the hook runs):
//   username+password : user_lookup_key, password, first_name, last_name
//   passwordless      : email, first_name, last_name
//   AuthKnight        : email, first_name, last_name   (email pre-verified)
//   completion        : ProfileFields values only (email belongs to the
//                       existing row; shown read-only, never submitted)
FuncUserRegister func(ctx context.Context, userID string, fields map[string]string, options UserAuthOptions) (registeredUserID string, err error)

Replaces — the following are deleted:

  • ConfigUsernameAndPassword.FuncUserRegister
  • ConfigOtp.FuncUserRegister
  • ConfigAuthKnight.FuncUserRegister
  • ConfigShared.FuncUserProfileUpdate (and authImplementation.funcUserProfileUpdate + Get/SetFuncUserProfileUpdate)

One hook, one signature, one place in config (ConfigShared) — registration semantics are a shared concern, not a per-method one.

4. Constructor + validation changes

  • new_passwordless_auth.go, new_username_and_password_auth.go: config.EnableRegistration && config.ConfigShared.FuncUserRegister == nil → error (message reused: MsgRegistrationFailedFn). The check moves from the method config to the shared config.
  • new_authknight_auth.go: config.ConfigShared.FuncUserRegister == nil → error.
  • Empty registeredUserID on the create path: if userID == "" and the hook returns ("", nil), the password method falls back to FuncUserFindByUsername / FuncUserFindByEmail (one release cycle of tolerance); all other methods treat it as an error ("user register returned empty id"). Long-term the fallback is removed — the contract is "return the ID".
  • Completion path stays optional: userID != "" with the hook unset keeps today's behaviour — request rejected with a clear message (MsgInternalServer + logged), since the host opted into completion by enabling CreateUserOnAuth incomplete accounts but provided no persistence hook.

5. Semantics hosts implement

// Canonical host implementation — one function for both paths.
FuncUserRegister: func(ctx context.Context, userID string, fields map[string]string, options types.UserAuthOptions) (string, error) {
    if userID == "" {
        return userStore.Create(ctx, fields)   // insert, return new ID
    }
    return userID, userStore.Update(ctx, userID, fields) // update, return ID
},
  • Hosts that store credentials separately (password column vs profile columns) branch on fields[types.FieldPassword] != "" — only ever set on the username+password create path, never on completion.
  • Hosts whose register form collects a credential the completion form must never touch are protected structurally: the completion branch's CollectFields(r, ProfileFields) only reads declared names, so a forged password=... form key never reaches the hook on the update path.
  • Hosts wanting strictly create-only or update-only behaviour return an error on the unwanted branch — the API surfaces it as a normal error response.

6. Relationship to the fields-map proposal

The two proposals compose but are separable:

  • Fields-map first, merge second: the 2026-10-31 proposal leaves FuncUserProfileUpdate(ctx, userID, fields, options) and three FuncUserRegister(ctx, fields, options) variants; this proposal then deletes three of the four and adds the userID parameter to the survivor. A second, smaller breaking pass.
  • Together: one breaking release where all user-write hooks collapse straight to the final signature. Recommended — host code is migrated once, not twice.
  • Merge only, no fields map: also coherent — FuncUserRegister(ctx, userID, firstName, lastName, options) with credentials via options — but re-opens the positional-parameter problem the fields map solves; not recommended.

7. Naming

This proposal is written in the vocabulary of 2026-11-02-user-lookup-key-naming.html, which lands first. Under that vocabulary userID is the user record's primary key (the positional parameter and return value of this hook), userLookupKey is the sign-in lookup key (a fields key, FieldUserLookupKey), and email names genuine emails. The unified hook is specified with that final naming — no second rename pass over brand-new signatures.

Explicitly Out of Scope

  • Changing when the hooks fire — ProfileCompletionRule, RegisterFirstRule, verification policies all unchanged.
  • FuncUserExists/FuncUserFindBy* hooks — still needed for login paths; only their post-registration re-lookup use shrinks.
  • Profile editing (settings page) — a future FuncUserUpdate concern; the unified hook is strictly for the registration flows (/auth/register).
  • Removing the FuncUserFindByUsername/findByEmail fallback for empty returned IDs — one release of tolerance, then removal.

Suggested Order

  1. ConfigShared.FuncUserRegister (unified signature) + authImplementation.funcUserRegister + Get/Set; delete the four old fields/hooks.
  2. Constructors ×3: shared-config validation; delete per-method wiring.
  3. api_register: completion branch + verified-token branch → unified call; drop the passwordless register/findByEmail adapter.
  4. core/register_with_username_and_password.go + api_register_code_verify: use returned ID; findBy* fallback for ("", nil).
  5. internal/testutils/auth_shared.go, examples, docs (docs/*.html tables), CHANGELOG entry.

Risks / Open Questions

  • Breaking — accepted: every host migrates all four hooks to one. Migration is mechanical and usually a deletion: hosts currently implement register + completion as near-identical bodies and can now share them.
  • Upsert is a stronger contract than create: the host must handle userID != "" even if it believes completion never fires. Mitigation: documented contract + the hook can error on the branch it doesn't support; the API surfaces it cleanly.
  • password in the fields map on update: structurally impossible on the completion path (declared-keys-only collection), but a host that ALSO wires the hook elsewhere must still branch on userID, not on key presence, for create-vs-update.
  • Naming: FuncUserRegister chosen because both paths are "registration" in package vocabulary (the completion form is the register page). Alternatives considered: FuncUserSave, FuncUserUpsert — rejected: vaguer, and "register" already covers the semantics including first/last-name-only writes.
  • Return value on update: returning userID (not just error) keeps the signature uniform; callers ignore it on the update branch.
  • UserAuthOptions.UserExists bool — considered, rejected (decision 2026-11-02): a flag duplicating userID != "" would create two sources of truth that can disagree (userID="u1", UserExists=false), and UserAuthOptions is delivered to every hook — a field only meaningful inside FuncUserRegister invites misreading elsewhere (a false zero-value in a logout hook looks like a bug). userID == "" remains the single discriminator; the host's if userID == "" { create } else { update } idiom is documented in §5.
