dracory/auth — proposal

Store Raw, Escape at Render

Status: Implemented Date: 2026-11-02 Scope: internal/api/api_register, internal/api/api_password_restore, release notes Blocks/relates: extensible-registration-fields proposal

Motivation

The register and password-restore APIs HTML-escape first_name / last_name at collection time — before validation, before the temp-key payload, before host callbacks see them:

// internal/api/api_register.go — 4 separate blocks, same pattern
firstName := html.EscapeString(req.GetStringTrimmed(r, "first_name"))
lastName  := html.EscapeString(req.GetStringTrimmed(r, "last_name"))

// internal/api/api_password_restore.go:134-135 — same pattern

Escaping is a presentation concern. Applying it at the boundary corrupts the data itself:

  1. Stored data is no longer the user's name. O'Brien becomes O'Brien in the temp-key payload, in the host's user table, forever. Every non-HTML consumer — JSON APIs, CSV exports, search indexes, mail-merge plain text, mobile clients — receives mangled data.
  2. Double-escaping downstream. Any consumer that correctly escapes at render (Go templates, hb, React) renders O&#39;Brien. The escaped-at-origin value is broken in both directions — raw consumers see entities, safe consumers see double entities.
  3. It generalises badly. The extensible-fields proposal (2026-10-31) carried this pattern into CollectFields. Escaping must never run on arbitrary declared fields — a password key or any value with <>& would be silently corrupted. This is the blocker for treating credentials as ordinary map values.
  4. The safety it pretends to give doesn't exist. The package cannot guarantee host-side XSS safety — hosts render these values in templates the package never sees. Escaping at origin only corrupts data while leaving the actual responsibility where it always was: with whoever renders.

Design Principle

  • Store raw. API handlers pass the submitted value through req.GetStringTrimmed and onward unmodified — to the temp-key payload, to FuncUserRegister, to FuncUserProfileUpdate, to options.Fields.
  • Escape at render. The package's own pages already escape via hb (.Text()/.Value() escape by default). Any future prefill of submitted values (e.g. completion form FuncUserProfile values) renders raw → hb escapes — correct, no double-escape.
  • Display-time escaping stays. utils/login_alternatives.go escapes strings it builds into markup — that's render context, and it stays untouched. The rule is positional: escape where markup is produced, never where data is collected or transported.
  • Breaking behaviour change — accepted. Hosts that relied on pre-escaped names and render them raw become XSS-exposed. Documented in release notes; correct data integrity outweighs preserving a defensive crutch that never actually transferred the responsibility.

Remove the now-unused html import in both files.

2. CollectFields (extensible-fields proposal) inherits the rule

The shared collector in the sibling proposal is amended: no escaping — raw trimmed values into the fields map. This makes fields["password"]-style credential keys safe and unblocks the flat FuncUserRegister(ctx, fields, options) signature discussed there.

3. Verification that render-side escaping holds

  • Audit every place the package renders user-supplied values into markup (page_register verified-email display, future prefill paths): must go through hb text/attribute builders, never string concatenation into HTML.
  • shared.FieldInput (sibling proposal) sets values via .Value()/.Text() — escaped by default.

4. Release-note / docs entry

CHANGELOG + README migration note: "Registration and password-restore callbacks now receive raw first/last names. If your templates render these values without escaping, add escaping — or validate/reject markup characters in FuncUserRegister."

Explicitly Out of Scope

  • Retroactively un-escaping already-stored host data — hosts' problem.
  • Input validation (rejecting <script> in names) — orthogonal; hosts can add a Validate func per the fields proposal, but the package does not impose a name-character policy.
  • Changing utils/login_alternatives.go — its escaping is render-context and correct.

Suggested Order

  1. Remove html.EscapeString at the 5 collection blocks + drop unused imports.
  2. Render-side audit (page_register + any prefill) — confirm hb escaping everywhere.
  3. Tests: raw round-trip assertions replacing any escaped-value expectations.
  4. Amend sibling proposal: CollectFields stores raw.
  5. CHANGELOG/README migration note.

Risks / Open Questions

  • Host XSS regression: any host rendering firstName raw (trusting package escaping) becomes exposed — the reason this is a documented breaking change, not a silent fix.
  • Should the package also sanitise? No — sanitisation is a data-policy decision (some hosts want O'Brien, some want to reject <>); the fields proposal's Validate hook is the right extension point.
  • Email templates: host templates injecting names into HTML emails must escape — same rule, stated in the migration note.
