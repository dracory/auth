dracory/auth — proposal

Uniform Lifecycle Hooks — Consistent Pre/Post Callbacks Across Methods

Status: Draft — revised 2026-11-15 (acknowledges existing ObservabilityHooks) Date: 2026-11-15 Scope: types, internal/api/* Inspired by: MadAppGang/identifo — plugins/, user_data_provider.go
⚠ POSSIBLY NOT NEEDED — overlaps ObservabilityHooks (2026-11-15)
types.ObservabilityHooks already records login, registration, rate-limit, session, password-reset and impersonation attempts. Adding a second notification surface doing ~80% the same work is duplication, not extension. If this proceeds it should replace ObservabilityHooks (one surface), not coexist with it — otherwise the package ends up with three hook surfaces.

Motivation

identifo exposes plugin extension points where host code runs at defined lifecycle moments — after login, after register, on password change — so hosts can attach side effects (audit logs, analytics, CRM sync, welcome emails) without the library knowing about them.

dracory/auth's extension points today are per-method and asymmetric: some flows have observability hooks (impersonation audit, structured logging), others end silently. A host that wants "log every successful auth event" must wrap handlers or infer it from session writes.

Update 2026-11-15 — correction: the "ends silently" framing below predates types.ObservabilityHooks, which already provides RecordLoginAttempt, RecordRegistrationAttempt, RecordRateLimitHit, RecordSessionCreated, RecordPasswordReset and RecordImpersonation* (metrics-oriented, success/error pairs, no event payload). This proposal should therefore be read as unifying and enriching that surface — one event struct carrying context the flat Record* methods cannot express — not as filling a void.

Design

1. A single event surface

// types/hooks.go
type AuthEvent struct {
    Kind    AuthEventKind // AuthEventLogin, Register, Logout,
                          // PasswordReset, ImpersonateStart, ImpersonateStop, ...
    Method  string        // "password" | "otp" | "magic_link" | "authknight" | "oidc"
    UserID  string
    Email   string
    Success bool
    Err     error  // set on failed attempts
    Meta    map[string]string
}

// FuncOnAuthEvent is invoked after each auth lifecycle event,
// success or failure. Errors returned are logged, never propagated
// (a hook failure must not break authentication).
type ConfigHooks struct {
    FuncOnAuthEvent func(ctx context.Context, event AuthEvent)
}

2. Invariant: every auth-affecting endpoint emits exactly one event

EndpointKindEmitted on failure too?
login (all methods)AuthEventLoginYes — Success=false, feeds audit/brute-force detection
registerAuthEventRegisterYes
logoutAuthEventLogoutNo (nothing to deny)
password restore/resetAuthEventPasswordResetYes
impersonate start/stopAuthEventImpersonate*Yes — already audited; unified under this surface

3. Non-blocking, never fatal

Hooks run synchronously after the response is prepared but errors only log — the auth outcome is already decided. Hosts needing async work spawn their own goroutine inside the hook.

Relationship to Existing Callbacks

This does not replace data callbacks (FuncUserStoreAuthToken etc.) — those are required reads/writes. Hooks are pure notification: the library works identically with FuncOnAuthEvent = nil. Existing impersonation audit hooks fold into the unified event for v2, keeping the old fields for compatibility.

Security

  • AuthEvent never carries passwords, codes, or tokens
  • Failed-login events include Err but hosts must not echo it to users (documented)
  • Hook panics are recovered — a buggy hook cannot take down auth

Out of Scope

  • Mutating hooks (e.g. "veto this login") — notification only in v1; a FuncBeforeLogin gate can be proposed separately if needed
  • Event persistence/queueing — the host's hook can write wherever it wants
