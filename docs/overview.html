Package Overview: dracory/auth

Last Updated: 2026-10-29

What is dracory/auth?

dracory/auth is a batteries-included authentication library for Go that provides ready-to-use authentication flows with minimal setup. It is implementation-agnostic — you bring your own database, session store, and email service; the library handles the authentication logic, UI pages, and API endpoints.

Core Philosophy

  1. Four Login Methods, One Composable Mux
  2. Email OTP (passwordless) — email-based verification codes
  3. Magic link — single-use emailed sign-in links
  4. Username/password — traditional authentication with password storage
  5. AuthKnight — delegated hosted login (external service verifies the user)

Methods are mounted together behind a single mux via NewMultiMethodAuth. The first method owns <endpoint>/login; secondary methods mount at <endpoint>/login-<name>. Custom methods implement the public types.Method interface — no library change required.

  1. Complete Solution
  2. Pre-built HTML pages for login, registration, password reset
  3. JSON API endpoints for SPA/mobile apps
  4. Authentication middleware for protecting routes
  5. Customizable email templates
  1. Production-Grade Security
  2. Structured error handling with error codes
  3. CSRF protection and per-route rate limiting
  4. OTP codes bound to random nonces (not store keys)
  5. Session invalidation on password reset
  6. Secure cookie defaults and input validation
  7. Structured logging for audit trails
  1. Flexible Storage + Hooks
  2. You implement the storage layer via callback functions — works with any database (SQL, NoSQL, in-memory)
  3. types.PostAuthHooks drives the shared post-authentication pipeline: allowlist → find-or-create → active check → session → cookie → redirect
  4. Optional capabilities (session store, temp-key delete, post-auth hooks) are attached via type-asserted setters — the public interfaces stay stable

🔑 Multi-Method Composition

a, _ := auth.NewPasswordlessAuth(cfg)          // shared impl serves otp + magiclink
p, _ := auth.NewUsernameAndPasswordAuth(pcfg)  // password impl

mma, err := auth.NewMultiMethodAuth("/auth", []types.Method{
    auth.NewPasswordMethod(p, nil),                 // primary → /auth/login
    auth.NewOTPMethodWithPage(a, nil),              // → /auth/login-otp
    auth.NewMagicLinkMethodFromAuth(a, nil, linkCallback), // → /auth/login-magiclink
})
mux.Handle("/auth/", http.StripPrefix("", mma.Router()))
  • First method mounts at GET|POST /auth/login; later methods at /auth/login-<name>
  • Method callbacks (/magiclink-callback, /authknight-callback) mount once each
  • RouteProvider.ExtraRoutes() mounts method-scoped routes (OTP code-verify, password restore/reset) only when that method is present
  • LoginAlternativesHTML renders an "OR — use another method" fragment for login pages

🔗 Post-Auth Pipeline

Every method's verify path funnels through core.PostAuth when any PostAuthHooks are configured — one place for allowlist checks, user find-or-create, active validation, session creation, cookie writing, and redirect resolution. When no hooks are set, the legacy per-flow behavior (token + FuncUserStoreAuthToken) is used.

🔑 Key Flows

Email OTP

POST /auth/api/login → generate code → FuncTemporaryKeySet → FuncEmailSend → POST /auth/api/login-code-verify → post-auth → session/token + cookie

Magic link

POST <login path> → store MagicLinkPayload{email, token, return, remember} under a nonce key → EmailSend/EmailEnqueue the link → GET /auth/magiclink-callback?token= → post-auth → redirect

Username/password

POST /auth/api/login → FuncUserLogin(username, password) → post-auth → token + cookie. Recovery via /password-restore + /password-reset (session invalidation built in).

AuthKnight

Login page redirects to the hosted AuthKnight flow → GET /auth/authknight-callback?once= → verify once with AuthKnight's /api/who → post-auth (existing users) or register-redirect with a verified-email temp key (new users).

🔒 Middleware

  • WebAuthOrRedirectMiddleware — resolves token → userID into context; redirects to login on failure
  • ApiAuthOrErrorMiddleware — same check, JSON error on failure
  • WebAppendUserIdIfExistsMiddleware — optional auth, never blocks
  • auth.GetCurrentUserID(r) — retrieve the authenticated user ID
